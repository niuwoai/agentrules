# 需求到验收与经验反馈 · 填写示例

> 本文件由 [需求规则](../../requirements.md) 和 [模板入口](../../templates/delivery/README.md) 索引。以下是虚构场景，仅展示填写和转换方式；没有真实用户、Issue、提交、测试 run 或已验证结论，不可用作交付证据。

## 1. 原始诉求与归并

假设已有业务项目收到反馈：“筛选列表后导出，文件里还有没筛选的数据。”

- 主记录：RQ-EX-001，沿用示例任务系统的编号。
- 来源：本示例的虚构反馈；实际项目填写真实请求 / Issue 链接或脱敏摘要。
- 用户 / 场景：有导出权限的用户，先筛选列表，再导出。
- 当前行为：反馈称导出包含未筛选项，尚未复现；不能直接认定根因。
- 目标：导出数据遵守选定范围和用户数据权限。
- 优先级：按实际影响、数据风险和时效确定；本示例没有用户数量、期限或事故级别，不编造评分。
- 归并：同筛选条件的重复反馈可关联主记录；不同角色或权限边界的反馈先保留差异，不能直接覆盖。

这是已有项目，只查看列表、导出、权限的相关参考，不重新询问平台、数据库和品牌方向。

## 2. 待澄清与范围

| 问题 | 推荐 / 影响 | 状态与阻塞范围 |
|------|-------------|----------------|
| 导出当前页还是全部筛选结果？ | 先查已有产品定义；无约定时建议明确选择全部筛选结果 | 待澄清；暂停依赖导出范围的实现，可继续复现与定位 |
| 导出权限是否与当前角色的数据范围一致？ | 复用已有权限契约，不因导出扩大权限 | 已有约定可引用；如存在冲突则先交有权决定者处理 |

假设真实项目随后确认“全部筛选结果”：在原记录补上真实结论与依据，再将范围设为就绪。若当前请求本来已明确这点，直接沿用，不重复确认。

本次包含筛选范围一致、权限不扩大、空结果行为；文件格式改版、异步任务和导出性能优化不在本次范围。需要新增目标时另记范围变化，不趁修复顺手实施。修复授权也不自动包含对外发布。

## 3. 验收与实施交接

以下仅为检查计划，各项状态均是待执行；实际项目须记录需求修订与候选 SHA / 产物和真实结果。

| 条件 | 预期结果 | 检查计划 | 实际状态 |
|------|----------|----------|----------|
| AC-1 筛选结果 | 导出记录满足全部选定筛选条件，范围覆盖已确认的全部结果 | 构造分页和组合筛选夹具，比较预期标识集合；先确认旧行为能暴露原问题 | 待执行 |
| AC-2 权限边界 | 不能导出超出当前用户权限的数据 | 用两个权限范围不同的角色验证成功及越权拒绝路径 | 待执行 |
| AC-3 空结果 | 沿用已有契约：本示例假设输出只有表头的文件 | 空夹具验证无额外记录；实际项目先引用真实约定 | 待执行 |

任务记录可与需求合一；如拆给列表和导出两个任务，则都关联 RQ-EX-001、当前需求修订和各自验收条件，明确接口和集成人。检查失败、没执行或环境不可用均保持未通过，不先填“已验收”。

## 4. 范围变化和证据处理

如果实施中又要求“导出顺序也与列表相同”：

1. 先判断已有约定是否已包含该行为；新增范围时记录有效决策和新的需求修订。
2. 增加排序条件，并评估列表查询、导出及其检查的影响。
3. 旧排序证据无效；原集合和权限证据能否复用，按查询 / 实现是否变化及候选对象给出理由，不能直接沿用所有旧绿测。
4. 完成受影响重验后，才按当前范围得出验收结论；若排序后置，须保留其决策和未交付边界。

## 5. 生成或更新经验记录

若真实调查确认“列表与导出各自实现筛选，原验收只检查文件能否下载”，就同时存在可复用的错误假设和验收遗漏，触发经验反馈。

先查项目已有经验位置及同类记录；有主记录就更新，无记录才按 [lesson.md 模板](../../templates/delivery/lesson.md) 创建。若项目已有 `LESSONS.md`，先读再增补；若采用 `docs/lessons/<ID>.md`，给所属入口增加摘要和链接，不并行维护相同正文。

示例记录应这样区分事实与计划：

- 事件：关联需求 RQ-EX-001 和实际修订；真实发生时间、版本和影响由项目填写。
- 原因：上述根因只有在实际定位支持时才记为事实；本示例没有调查证据，仍属假设。
- 漏检点：原检查只证明下载成功，没有证明筛选和权限边界。
- 防复发计划：补筛选、空结果和越权场景；把检查接入项目常用命令和实际 CI job。
- 反例验证：在真实旧行为下暴露原缺陷、修复后通过；当前没有实际运行，状态为待验证。
- 适用范围：先作为本项目列表与导出的一致性经验；跨任务稳定成立且前提明确后才考虑提炼通用规则。
- 晋升状态：不因写完模板或补了测试文件就标为已验证；没有执行入口及反例证据时保持待验证。

## 6. 关闭与反馈

真实项目只有在当前范围的必需条件通过、指定验收者适用时已有结论，并明确遗留项处置后，才记为已验收。同时单独报告已实现、已验证、已合入、已分发或已部署的实际阶段。

经验验证可以有独立的后续负责者和计划；若其防线本身属于本次必需验收，则未完成时不能关闭需求。遇到反证则修正或废弃原经验并保留依据，不再复制一条互相冲突的长期规则。
